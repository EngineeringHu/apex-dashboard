评估日期：2026-10-11；首版实现日期：2026-10-12。状态：源码已实现，尚未部署或转换真实日记。每次手动操作只处理当时已有日记；后续 Calendar 等创建的明文保持原样，需要时再手动加密。

首版在 Apex 设置中使用“日记加密”开关；开启时转换 `日记/` 下现有 Markdown，开启后可点“加密现有明文日记”补加密。密文后缀为 `.apexdaily`，打开时只显示锁定提示。关闭开关时输入已有统一密码，恢复同名 `.md`。中断时使用设置中的“继续切换”。独立恢复命令为 `node tools/decrypt-daily.mjs <文件.apexdaily> --verify` 或 `--output <日记目录外文件.md>`；它只导出，不覆盖原密文或现有明文。

### “回退写入工作台”指什么

这是 [daily-notes.ts](../src/daily-notes.ts) 中 `insertTaskForDay()` 的行为，由 Apex 日历添加任务入口调用：

1. 对应日期的日记存在，就向该日记写任务。
2. 对应日记不存在，尝试向今天的日记写任务。
3. 两者都不存在，尝试写入当前工作台的第一个待办列表；没有待办列表就追加到工作台末尾。
4. 工作台文件也不存在，才尝试创建对应日期的日记。

写入的是新增任务。此逻辑属于 Apex 的任务日历，与第三方 Calendar 的日记创建流程分开。

首版只补一个判断：如果本次要读取或写入的日记实际已加密，则提示先解密并结束本次操作。不能把“已加密”误判成“从未创建”后继续回退；真正不存在的日记仍沿用原规则。

## 操作和状态

可保留用户要求的“日记加密”开关，但明确它表示手动转换管理，不是持续保护整个目录：

| 操作 | 处理范围 |
| --- | --- |
| 开启加密 | 对开始操作时确定的现有明文日记执行一次批量加密 |
| 加密新增日记 | 开关开启期间仍可手动执行，只处理本次发现的普通日记，跳过已有密文 |
| 关闭加密 | 验证密码，将已加密日记恢复至原路径；保留后来新建的、不冲突的明文日记 |
| 重启、Calendar 新建、闲置 | 不自动转换，不干预 Calendar，不重定向第三方写入 |
| 转换中或待恢复 | 暂停涉及本次文件的 Apex 操作，显示进度或继续恢复入口 |

设置页显示实际数量，例如“已加密 2 篇，未加密 1 篇”。不能仅因开关开启就显示“日记目录全部受保护”。数量可在打开设置、手动刷新及转换结束时读取，不需要监听新建事件自动加密。

范围固定 `日记/` 及子目录，包含非日期文件名。首版正文按完整文件处理，原属性、空白及换行保持一致，空文件不补模板。开启或补加密前若目录内有附件及其他非 Markdown 文件，操作报出具体路径并停止；首版不加密附件。目录外附件和历史备份不自动纳入。

## 明文与密文并存时的规则

判断应以文件实际状态和可验证的原路径对应关系为依据，不能对整个日记目录一律禁止操作。

- 已加密日记：关联、跳转、读取、写入只提示“该日记已加密，请先关闭日记加密开关并完成解密”，不自动解密。
- 后续新建的普通日记：沿用原有打开、编辑、关联和筛选流程；需要时用户再次手动加密。
- 关联元数据保留原 `.md` 路径。解密恢复同一路径后继续有效，无需改成密文链接或引入新的关联系统。
- 筛选和任务查询继续使用普通日记及其他笔记；提示部分日记已加密、结果未包含这些文件。仅查询加密日记且没有明文结果时显示需解密状态。
- 在加密过程中清除本批次日记的旧查询结果、缓存、弹窗和预览，防止已经显示的正文继续留在界面；不得清空或改写其他笔记内容。

### 同名冲突必须保护

Calendar 可以重新创建已加密日期对应的同名 `.md`。例如目录同时出现 `2026-10-10.apexenc` 和新的 `2026-10-10.md`，两者可能含有不同内容。

首版处理方式：

1. 两份均保留，不自动覆盖、删除或合并。
2. 再次加密和解密都先预检；存在此类冲突时，在批次写入前停止并列出具体路径。
3. 提示先将新建明文改名保存，再继续转换；不代替用户判断哪份应该保留。
4. Apex 的旧关联遇到此类歧义时提示冲突，不悄悄打开另一份同名新日记。

这项检查是允许第三方继续新建明文后必须保留的数据保护，不属于第三方插件适配。

## 首版代码范围

新增集中模块：

- `src/secure/daily-mode.ts`：手动批量转换、状态与数量、原路径、预检、校验及中断恢复。
- `src/secure/daily-access.ts`：按文件判断普通、已加密、冲突、转换中状态，提供统一提示与查询排除信息。
- 使用独立 `.apexdaily` 后缀和小型锁定提示视图，底层仍复用 v2 密文格式；不引入正文编辑器。

对现有代码做小范围接入：

| 部分 | 需要保留的修改 |
| --- | --- |
| 设置、启动和提示 | 独立状态加载、开关、加密新增按钮、数量及恢复入口 |
| 加密 Worker 和文件封装 | 复用现有算法及统一密码；需要时补完整原文入口，避免周记分区解析限制日记内容 |
| Apex 日记新建、关联、跳转及写入 | 遇到已加密或有歧义的目标时提前返回；其他目标走原逻辑 |
| 文件夹筛选、DQL、任务及相关统计 | 排除已加密文件，清理本批次缓存，撤销过期异步结果；保留普通笔记结果 |
| 日记弹窗和预览 | 加密前保存并关闭本批次文件；等待脱离常规工作区的编辑弹窗保存完成 |
| 统一密码和转换互斥 | 日记仍有密文或待恢复记录时提示先解密再改密码；转换期间不允许其他操作终止其 Worker |
| 恢复工具与 Git 检查 | 能独立恢复日记；识别日记转换记录，避免提交未完成的转换状态 |

首版不接管或停用核心日记、Calendar，不包装它们的命令，不阻止它们创建明文，不做后台自动加密。这可以直接删除上一版方案中的第三方入口阻断和版本适配工作。

专用日记编辑器、加密状态下查询、自动解锁、关联路径迁移、跨目录密码轮换也不纳入。剩余工作量主要是转换、缓存清理和 Apex 自身提示；涉及文件仍可能较多，但多数是小幅接入，不应为追求文件数量少而遗漏已加密内容的访问或残留显示。

## 数据保护与正常业务恢复

- 操作开始先确定本批次清单，处理涉及文件的未保存编辑，校验文件类型、路径和目标冲突。
- 每篇生成密文并验证完整原文可恢复后，再清理相应明文；流程沿用既有准备、发布、验证和提交步骤。
- 保留原相对路径、正文、属性与换行；认证载荷保留原 `mtime` 和 `ctime`，恢复时尽力还原磁盘 `mtime`。文件系统的物理 `ctime` 不能设置，解密后可能变化；时间筛选若依赖物理创建时间，应以真实 Obsidian 回归结果为准。
- 错误密码、取消、文件损坏、写入失败及外部修改均不得覆盖或丢弃原数据；中断记录只保存密文、路径及校验信息。
- 解密后保留既有关联和筛选配置，待原生元数据和索引就绪再刷新界面。
- 目录中的新明文在主动处理前保持明文。密文文件名仍可见，旧 Git 历史、历史快照及范围外副本不因转换而消失。

## 为后续升级保留的最小基础

1. 继续使用已有密码学算法和 v2 密文封装，不另造一套密码体系。
2. 日记的恢复元数据具有独立版本号，原路径、文件时间、内容类型等写入受认证的加密载荷；记录格式与设置状态也分别带版本号。文件不应只依赖易丢失的 `data.json` 才能恢复。
3. 保持“转换能力”和“业务是否可访问”的接口分离。后续增加单篇解锁、自动加密或 Calendar 适配时调用这些接口，不要求改写旧日记。
4. 将首版密文保存为测试样本，后续版本必须通过旧文件读取和独立恢复回归。遇到不认识的版本停止处理，不猜测格式或覆盖原文件。

## 首版验收

使用合成文件和独立密码，清理后核对真实笔记哈希：

- 加密、解密恢复原路径和内容；日期日记、普通标题、空文件、属性、换行、子目录往返一致。附件目前在开启前报错，不进行转换。
- 已有两处任务关联在加密时提示、解密后恢复；实际不存在的日记继续原回退规则。
- 已加密旧日记与新建明文并存；新日记正常使用；再次手动加密不重复处理旧密文。
- Calendar 继续原行为；同名新建明文与密文冲突时两份完整保留，转换停止。
- 加密后没有本批次正文遗留在 Apex 旧查询结果、缓存和编辑弹窗中；普通日记及其他目录业务正常。
- 错误密码、取消、断电恢复、重复点击、写入失败、外部修改均不丢文件。
- 解密前后比较原有关联、筛选、任务及时间排序；周记工作台、表格和现有加密回归通过。
- 后续版本能读取首版密文；独立工具恢复不依赖界面状态或明文缓存。
