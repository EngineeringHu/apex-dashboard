## 1. 推荐方案与目标

在当前定制版 Apex 内增加分区加密存储、密码输入、受保护 Markdown 编辑视图和统一锁定管理。使用标准密码学库/API，不自行设计加密算法。参考 Meld Encrypt 的“仅在内存解密”原则；分区加密格式及 Apex 集成需要开发。

核心规则：**默认保护模式下，受保护周记从创建、编辑到自动保存，应用写入磁盘的始终是密文。每个分区有独立的密文和解锁会话，收起只锁定该分区，不影响其他仍展开的分区。** 用户主动开启的全量临时明文模式是明确例外，该期间正文及真实名称可从磁盘读取；提供持续状态提示与一键结束。

保护目标：在默认模式下，他人通过资源管理器、文本编辑器或复制受保护文件，无法直接读到正文；Apex 或编辑器未经密码解锁不显示正文。实现需验证应用自身不主动写出明文文件，不能承诺操作系统交换文件、休眠、转储和存储介质中绝对没有明文残留。用户要求暂不处理的 Apex 历史备份属于本轮保护范围之外，因此不能宣称整个仓库已无历史明文。

## 3. 方案对比

| 方案 | 磁盘正文加密 | Apex 展开/收起联动 | 结论 |
| --- | --- | --- | --- |
| 界面密码、隐藏文件、CSS 折叠 | 不满足 | 可以改变显示，但不保护文件 | 不满足核心要求 |
| 仅使用 Obsidian Sync 的端到端加密 | 本地库不因此加密 | 无 | 不能替代本地加密 |
| Meld Encrypt 整篇加密 | 作者文档明确仅在内存解密，使用 `.mdenc` | 当前 Apex 的扫描、解析和保存不能直接使用；也不是所需的分区隔离 | 可作为参考，单独安装不够 |
| Apex 集成标准加密存储与受保护视图 | 设计上满足 | 可按所需交互定制 | 推荐，须完成实现和验收后再迁移 |

Meld 的密码记忆/超时功能不能直接视为 Apex 的收起锁定功能。如果复用其代码，需要遵守许可证、固定兼容版本并验证文件格式；本方案默认不依赖两个插件互相访问私有内部对象。

依据：[Meld Encrypt 项目](https://github.com/meld-cp/obsidian-encrypt)、[整篇加密说明](https://meld-cp.github.io/obsidian-encrypt/whole-encrypted-notes.html)、[密码缓存设置](https://meld-cp.github.io/obsidian-encrypt/settings.html)、[Obsidian Sync 安全说明](https://help.obsidian.md/sync/security)。

## 4. 文件格式与使用体验

已确认使用专用扩展名且文件名保密，建议保存为 `周记/<随机UUID>.apexenc`。这是本项目拟定义的扩展名，并非声称已有该插件或标准。真实周记名称放入密文，锁定时显示“加密周记 · 短ID”，解锁文档信息后才显示真实名称；提供“看板”和“Markdown 文本”两种受保护视图。关闭插件后，文件继续保持密文。

文件内部按稳定分区 ID 保存多个独立密文块。表格、任务、备忘录等正文分别属于对应分区；frontmatter、横幅及分区外文本放入独立的“文档信息”密文块。磁盘上不保存完整明文 Markdown 副本。

锁定状态只显示通用分区类型（如“周计划表”“备忘录”）、展开按钮和锁图标。用户自定义标题随正文加密。图片和附件也使用随机 ID 文件名，真实名称、MIME 类型及展示标签存入密文。文件大小、修改时间、分区数量和排列顺序仍可见；本方案不隐藏“存在多少文件、何时修改”的元数据。

为避免通过设置泄露真实名称，默认模式下本模块写入的 `workspaceNames`、注册表、最近访问、workspace 状态、错误信息和 Git 提交信息只保留随机 ID 或通用标签；既有 Apex 备份按本轮范围排除。原先含真实名称的旧配置和笔记文档另列迁移清单。解锁文档信息只显示文档标题，不自动解锁正文；关闭其显示或锁定本周后清除该标题。首版允许锁定时按通用分区类型、随机短 ID 选择文件；临时明文模式则按用户选择显示真实名称。

如果必须保留 `.md`：可以保存只含格式标记与密文块的 Markdown 外壳，通过命令/菜单进入受保护视图。普通 Markdown 编辑器只会看到密文。原生编辑器有误删密文外壳的风险，并且只靠 `file-open` 事后切换视图不能覆盖所有编辑入口，所以此方案需要额外防误写设计，不推荐作为首版默认值。

分区交互已确认；以下多窗口和整篇编辑互斥规则为推荐实现：

| 操作 | 预期行为 |
| --- | --- |
| 启动 Obsidian、恢复上次工作台 | 显示锁定卡片，不恢复密码与明文 |
| 文件列表打开受保护周记 | 每次先提示密码；用户可选择仅打开文档信息和锁定看板，或打开整篇 Markdown 编辑；看板各分区仍各自展开验证，不记忆刚才的口令 |
| Apex 展开某个分区 | 每次都输入密码，只解密、解析并渲染该分区；其他分区保持当前状态 |
| 取消或输错密码 | 保持锁定，不创建空文档、不改变原文件 |
| 修改表格、勾选任务、编辑正文 | 统一通过加密存储层自动保存；不向旧 Apex 备份入口传递明文 |
| 收起某分区 | 保存该分区密文，移除该分区 DOM、明文模型和密钥；同一分区在其他窗口同步锁定，其他分区不受影响 |
| 关闭周记视图 | 保存并锁定该视图涉及的分区；建议同步锁定同一周记在其他窗口中的这些分区 |
| 切换到另一周 | 先保存并锁定上一周，再对下一周执行解锁流程 |
| 同一周打开多个标签或独立窗口 | 每次新展开仍要求密码，不因其他窗口已解锁而跳过；共用文件写入队列，同一分区的锁定同步广播 |
| 闲置 | 建议增加可配置的 5 分钟无操作自动锁定，作为收起/关闭之外的补充 |
| 最小化、系统锁屏、休眠 | 建议锁定全部；按 Windows 桌面环境验证实际事件。普通切到其他应用不立即锁定，继续遵守闲置计时，避免复制资料时反复输入 |
| 点击“立即锁定全部” | 锁定所有受保护周记，提供快捷键 |
| 主动“临时解密全部周记” | 输入一次密码，分批创建明文工作副本供原生搜索/Dataview 索引；显示状态及结束按钮，不在启动时自动执行 |
| 临时模式期间要求恢复分区锁定 | 先完成加密保存、校验和工作副本清理，再恢复分区模式；未清理完成不得显示“已锁定” |

“收起”确定指 Apex 的分区折叠按钮，例如收起整个周计划表。横幅、侧栏、任务树子项折叠仍属于排版操作；同时提供“锁定本周”和“锁定全部”的明确入口。

各分区使用独立随机内容密钥与密文，推荐使用同一个周记口令；采用下文的信封加密，避免全量解锁时为每个分区重复执行昂贵的密码派生。普通分区解锁只解包目标内容密钥，完成后不保留可解锁其他分区的原始口令或根密钥；收起后释放该分区内容密钥。用户主动开启的全量查询会话具有更大授权范围，不冒充普通分区模式。仅隐藏 DOM 而在查询结果或整篇模型中保留正文，不算已经锁定。

**整篇 Markdown 编辑与分区看板采用互斥模式。** 用户进入整篇编辑时再次输入密码，在内存解密所有分区并组装 Markdown，同时关闭/锁定同一周记的所有看板实例；此时界面明确提示“整篇已解锁”。保存时解析 Markdown 并按稳定 ID 重建各分区密文，校验段落、frontmatter、空白和顺序没有丢失；退出编辑后清除整篇文档与撤销历史，回到全部分区锁定状态。若同一周记的看板已重新打开并解锁分区，就不能同时保留整篇明文编辑器。这样“收起分区已锁定”不会与后台整篇明文编辑器并存。

分区 ID 的映射和 Markdown 原文片段需支持无编辑导出时逐字节还原，不能仅依赖现有 parse/serialize 的语义等价；解析失败或遇到无法表示的结构时保留原密文并报告错误。整篇编辑修改结构后先给出新增/删除分区的差异，禁止静默漏掉未知段落。

## 5. 加密与保存设计

首版建议用 Web Crypto 提供的 AES-256-GCM 做带完整性校验的加密，并采用“口令保护内容密钥”的信封结构。PBKDF2-HMAC-SHA-256 从口令和加密域的随机盐派生临时根密钥；再通过 HKDF 的用途、文件 ID、分区 ID 隔离各密钥包装用途；各分区正文使用独立随机内容密钥加密。加密域仅用于让同一次批量解锁复用昂贵派生的计算结果，不在普通会话中常驻根密钥。

同一加密域与口令版本的全量操作执行一次昂贵派生，再解包授权范围内的内容密钥；不同域/不同口令版本不能错误共用。派生盐、参数、域/版本 ID 及被包装的内容密钥随容器保存，保证独立脚本无需插件配置也能恢复。具体派生工作量在较慢的目标电脑实测后确定，设安全下限及读取上限；不能为了更快而静默降低已有文件的强度。采用标准算法本身不等于整个格式已通过安全审计，需检查密钥用途隔离及跨实现测试。[AES-GCM API](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt)、[密钥派生 API](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/deriveKey)。

实现要求：

1. 加密域盐、各分区内容密钥均使用密码学安全随机数生成。内容加密和密钥包装分别生成新的 96 位 nonce，同一密钥下不得复用；使用 128 位认证标签。
2. 容器含格式版本、加密域与口令版本、文件稳定 ID、派生参数与分区清单；每块含稳定分区 ID、被包装的内容密钥、相应 nonce 与密文。认证附加数据绑定格式版本、域/版本、文件 ID、分区 ID 和关键头字段，拒绝跨分区拼接、重复 ID、未知版本、超限参数和截断数据。
3. 容器另有认证清单记录合法分区 ID 和顺序；使用独立用途密钥认证，解锁时验证，清单变更需输入口令。常规分区编辑不更改清单且不解锁其他正文块；正文密文各自校验。重命名不改变稳定文件 ID。认证加密能检测篡改，不能单独防止整份容器或某块回退到旧的合法版本；冲突和历史恢复要另有规则。
4. 不存储密码，不在日志、localStorage、workspace 状态或配置 JSON 中保存正文或可直接解密的密钥。口令输入后尽快清空输入框；锁定后释放密钥与明文引用。
5. JavaScript 的垃圾回收无法保证清零所有内存副本；不得宣传为抵御内存取证的方案。正常修改口令可重新包装内容密钥并更新认证信息；若旧密钥可能泄露，则需轮换内容密钥并重加密正文和附件。两者都不撤销旧 Git 历史、旧备份的解密能力。密码学格式需版本化并在实现阶段独立检查。
6. 文件级队列串行保存；文档模型只保留已解锁分区明文，其他分区维持原密文。修改一块时读入最新容器并只替换该块，不用旧的整篇序列化结果覆盖其他块。异步解锁/保存用分区会话代数校验，锁定后旧回调不得重新显示正文。
7. 默认模式保存只写密文，本模块产生的临时文件、恢复文件也只能是密文。Apex 既有备份不在本轮改造范围，受保护存储不得把明文送入其入口。采用经目标平台验证的安全替换流程，不能假定简单覆盖具有崩溃原子性。
8. 对外部修改检测版本/摘要，出现冲突时保留双方密文，解锁后比较；禁止自动按文本合并密文，禁止静默覆盖另一设备改动。
9. 当前 `writeToDisk` 捕获并仅记录写入错误的行为需要改成可返回成功/失败；锁定不得在写入失败时显示“已保存”。安全遮挡与数据保存状态分别表达。
10. 锁定时先停止新编辑并遮挡正文，提交编辑框尚未触发 blur 的输入，排空保存队列；失败时尽量保留待重试的密文恢复副本。若连恢复副本也无法持久化，明确提示可能丢失最后修改，不能静默丢弃。

不依赖“退出 Obsidian 时再加密”：强制结束进程时没有可靠的退出回调。崩溃后磁盘仍是上一次成功保存的密文；最后未保存编辑可能丢失，应通过短间隔密文自动保存控制损失窗口。

不得全局修改 `vault.read` / `vault.modify` 来向所有插件透明返回明文，否则 Dataview、备份、预览等可能收到并保存明文。默认模式只在受保护入口解锁，其他插件读取到密文或不识别该类型；用户主动开启临时模式时，通过真实工作副本提供兼容性。

## 7. 边界、兼容与恢复

- **搜索与索引**：默认锁定时不可读正文；已选择主动全量临时明文模式，供现有 Dataview 与原生全文搜索索引。结束后重新加密有改动内容，清理本会话工作文件及已知缓存，具体见第 11 节。
- **Markdown 体验**：首版可提供独立源码编辑和安全阅读视图；不直接承诺与原生 Live Preview、所有编辑器插件完全兼容。渲染时应禁用可执行代码块处理器和自动远程资源，避免解锁内容被第三方渲染链路读取或发出外部请求。
- **附件（必须实现）**：当前只确认周记目录有一个 `.md`，未发现常见 Markdown 附件嵌入语法，但这不等于已审计全部外链。所有受保护图片/PDF等作为独立 `.apexasset` 密文文件存于 `周记/_assets/<随机UUID>.apexasset`。每个附件生成独立随机数据密钥，密钥及真实文件名只存在于引用它的分区密文中；解锁该分区才可解密附件。导入/粘贴由受保护视图接管，先在内存加密再写盘，不能调用会先落地明文的普通附件导入路径。
- **附件预览**：在内存解密，图片和支持的文件以内存 Blob 预览；锁定时撤销 URL、销毁预览窗口并释放引用。对必须创建临时明文文件才能外部打开的格式，只提供明确的导出动作。首版不自动加载远程图片或执行嵌入脚本。共用附件仍被另一个已解锁分区引用时，该已解锁分区内仍可查看；收起某分区不会撤销其他已授权分区的显示。
- **附件原件**：从库内普通附件迁移时，必须核查其他笔记引用；不能自动删除被其他笔记共用的原件。若原件继续作为明文保留，就不能声称该附件在整个库中已经保密，迁移报告必须显式列出。密文附件回收须在完整引用核验后执行，不能仅凭当前已解锁分区判断“未使用”。
- **同步（Git、多台 Windows）**：提交密文容器、密文附件、定制插件运行文件、公开格式说明及离线脚本；使用库内相对路径，不依赖 Windows 用户账号、DPAPI 或机器专属密钥。同步明文配置中不放密码和真实周记名称。详细提交、部署及冲突规则见下节。
- **已有副本**：按用户要求，Apex 的 `.dashboard-backup` 和插件 backups 暂不处理，不作为本轮实施前置条件。文件恢复快照、Git 历史、回收站、其他设备和手工备份也不会因新文件加密自动消失，已复制出去的明文不能追回。
- **插件信任**：Obsidian 不给社区插件提供可靠的权限隔离。恶意插件或已控制当前用户会话的程序可能读取解锁内容、捕获密码；本功能保护文件静态存储和正常界面访问，不承诺抵御此类攻击。[Obsidian 插件安全说明](https://help.obsidian.md/plugin-security)。
- **口令遗失**：无后门找回。密码只在本地对话框输入，不发送给聊天；用户用自己的密码管理器保管。可另外设计离线恢复密钥，但必须说明其保管责任。
- **独立恢复（用户明确要求）**：必须交付公开格式说明和离线解密脚本，验证不启动 Obsidian、停用/卸载插件后仍能凭密码导出标准 `.md`；密码通过交互输入，不能放命令行参数或日志。明文导出由用户明确选择目录和动作。
- **更新维护**：定制版与上游升级需要维护；不得让社区自动更新覆盖定制保护能力后还继续创建普通明文周记。停用插件时现有加密文件继续安全，但无法保证其他程序/插件不会向“周记”目录写入新明文文件。

文件恢复快照保存在库外，核心界面“清除历史”会删除整个库的快照，不能为了周记迁移直接执行该全量删除。[文件恢复官方说明](https://help.obsidian.md/plugins/file-recovery)。

### 独立脚本的具体交付约定

建议交付 `tools/decrypt-weekly.mjs`，使用 Node.js 内置密码学 API，无需 Obsidian 或 npm 第三方依赖；本机需有受支持的 Node.js。提供 Windows 启动说明；该文件本轮尚未创建，下例为计划的调用方式：

```powershell
node tools/decrypt-weekly.mjs "周记/<随机UUID>.apexenc" --output "D:/私密导出/周记.md"
```

- 在本地终端交互输入口令，密码不回显，不接受命令行明文密码参数；非交互输入需另行设计安全入口。
- 先验证格式、认证清单和全部分区，全部成功才创建输出文件；密码错误、损坏或认证失败均不产生部分明文输出。
- 输出为普通 UTF-8 Markdown，还原 frontmatter、分区顺序、表格、任务及文档其他文本。纯文本/未改写附件链接的原样恢复模式应逐字节还原；便携导出模式可将附件写入同级目录并重写为相对链接，此时明确不承诺 Markdown 字节完全相同。
- 默认一并验证所引用的附件是否齐全，提供“含附件便携导出”与“仅正文导出”选项；缺失附件需明确报告，不能伪装为完整恢复。便携导出先完成全部认证校验，再输出 Markdown 和附件，原密文均保留。
- 原 `.apexenc` 保持不变；默认拒绝覆盖已有输出，拒绝把明文输出到受保护周记目录，不默认往同步目录批量导出。
- 可增加整目录批量解密和只验证不导出的 `--verify` 模式；批量导出逐文件报告成功/失败，不打印正文和口令。
- 插件与脚本共享格式规范和互操作测试向量；测试同时验证“插件加密→脚本导出”和“旧版本容器→新版本脚本”。脚本必须仅凭容器、所引用的密文附件及口令恢复，不能依赖插件的 data.json 或 Obsidian 缓存。
- 用户主动导出的 `.md` 是明文文件，后续收起 Apex 分区不会再次加密这个导出副本。若未来需要脚本加密/重新导入功能，应作为独立命令实现，不能以覆盖原密文作为默认行为。

建议同步以下内容：

```text
周记/<随机UUID>.apexenc                  # 正文分区、受保护标题和清单
周记/_assets/<随机UUID>.apexasset         # 图片和附件密文

```

定制插件应标识独立构建版本，并制定防止社区更新覆盖的安装方式；开发时评估使用独立插件 ID 与保留当前 ID 的迁移成本，不能同时加载两份会处理同一文件的 Apex。配置只同步必要的公开选项，排除实际口令、会话数据、机器特定 workspace 状态和导出目录。检查现有 Git 忽略规则，确保运行文件和密文附件确实被跟踪；本轮尚未验证这些文件已受 Git 跟踪。

另一台电脑：安装兼容版本 Obsidian，拉取完整仓库，按说明启用定制版插件；若运行文件变化需重载插件或重启。无需构建源码；离线脚本另需 Node.js。第一次使用每个分区按相同规则输入用户口令。不可承诺 Git 拉取自动替用户启用社区插件。

在 `.gitattributes` 中把 `*.apexenc` 和 `*.apexasset` 配置为不做文本 diff/merge（如 `-diff -merge`），避免生成破坏容器的冲突标记。首版按“一台电脑编辑完→等待密文保存→提交推送；另一台拉取→再解锁编辑”使用。拉取时推荐先锁定工作台，插件仍需检测活动会话期间的外部文件变更。

多设备同时改同一容器时，Git 必须暴露冲突，不能用 `ours` / `theirs` 静默丢弃另一份；保留两份密文，用密码解锁后选择或逐分区合并，再保存新密文。自动语义合并不作为首版必需能力。丢失附件、附件与容器不同步、口令变更提交不完整都必须报错。

**历史处理是上线前的独立步骤。** 如果旧明文正文、文件名、配置或附件已进 Git，删除当前工作区文件并提交不能移除历史。先做可验证的加密备份，再列出需要从历史移除的具体路径、旧配置字段及复制在文档中的真实名称。历史重写与强制推送会影响其他克隆，届时必须明确确认范围，协调其他电脑重新克隆/重置同步基线；本轮不执行。远端旧对象、托管服务备份以及已被复制的内容不能保证被彻底清除，不承诺追溯保密。

## 8. 实施与迁移顺序

1. 需求已齐：多台 Windows + Git，分区独立锁定，每次打开/展开验证，专用扩展名，文件名/附件加密及独立解密脚本；本轮审阅方案后再开发。
2. 保留当前定制功能基线，在隔离测试库中开发；使用虚构周记和临时测试密码，不复制真实正文到测试日志。
3. 先用虚构数据验证 Dataview 模式与性能可行性，验证分区加密格式与独立恢复，再接入看板、编辑器、附件和自动锁定；最后验证另一台 Windows 干净克隆和插件部署。Apex 备份的改造/迁移暂不做。
4. 生成本轮受保护文件清单，选择一次性的迁移回退副本位置并确保其加密且可恢复；不为迁移在库内新建明文 zip/副本，不把整理既有 Apex 备份作为前置工作。
5. 用户在本地设置口令。迁移时暂停相关编辑与同步，在内存读取原 Markdown，生成新密文，重读解密并与原内容逐字节校验。
6. 全部校验和独立恢复成功后，更新工作台注册、链接及入口，清理现役明文；保留可恢复的加密迁移记录。中断可以继续，不覆盖唯一可用副本。
7. Git 历史、库外恢复快照另列处理范围；Apex 旧备份按用户要求暂不处理。涉及丢弃历史和不可逆删除时，先明确具体范围；普通删除不等于 SSD 安全擦除。
8. 恢复同步，逐台核验，旧设备不得再编辑旧明文副本。迁移回滚也不能默认重新生成整目录明文。

## 11. Dataview 全量临时解锁与重新锁定

### 11.1 已验证的兼容约束

检查了本库 Dataview 0.5.68 的实现：`FullIndex` 初始化枚举 Markdown 文件，依赖 Obsidian 的 metadataCache；文件导入后将解析数据写入 IndexedDB 持久缓存；目录查询及页面解析也依赖真实文件路径。由此不能把“解密字符串”或“往 pages Map 塞对象”当作已经完整兼容 Dataview。

Dataview 主要查询 frontmatter、内联字段、任务、标签等索引数据，并不等于任意正文全文搜索。原生全文搜索是另一条数据链路。依据：[Dataview 索引源码](https://github.com/blacksmithgu/obsidian-dataview/blob/master/src/data-index/index.ts)、[缓存源码](https://github.com/blacksmithgu/obsidian-dataview/blob/master/src/data-import/persister.ts)、[可查询数据说明](https://blacksmithgu.github.io/obsidian-dataview/annotation/add-metadata/)、[插件 API 文档](https://blacksmithgu.github.io/obsidian-dataview/resources/develop-against-dataview/)。

### 11.2 已选择：临时明文兼容模式

用户已明确选择“允许临时明文，优先兼容原生搜索和 Dataview，结束后重新加密清理”。不再把内存虚拟文件/自建 Dataview 查询引擎作为首版实施内容。

提供两个明确入口：“临时解密全部周记”和“结束临时解密并锁定”。平时继续使用分区加密模式；只有用户主动输入密码开启本模式时，才在库内生成临时普通 Markdown。此期间真实名称和正文对 Windows、原生搜索、Dataview 及其他插件可见。状态栏持续显示“临时明文已开启 · N 篇”，不能同时声称这些内容已因某个分区收起而锁定。

两种编辑模式互斥：临时模式期间关闭/锁定原受保护编辑视图，原生 Markdown 与 Dataview 操作临时工作副本；结束后才恢复 Apex 逐分区展开需密码的行为。原定“每次分区展开需密码”仍适用于日常保护模式，用户主动开启全量临时解密是显式例外。

### 11.3 临时目录、Dataview 与搜索兼容

建议临时目录放在 `周记/_临时解密/<会话ID>/` 下，里面是原始名称的 `.md`，且使用非隐藏目录，确保 Obsidian 正常索引。密文容器及加密附件继续留在原位置，作为上次安全状态，绝不先删密文再解密。

- 常见的 `FROM "周记"` 目录查询可以覆盖该子目录，需在原型中核实；Dataview 本来不索引 `.apexenc`，避免重复创建所谓虚拟 Markdown 索引。
- 精确文件路径、直接引用旧文件名、依赖 `file.folder` 的分组和排除子目录的查询，可能需要改为临时路径或调整一次查询；不承诺所有已有查询零改动。
- frontmatter、内联字段、任务、标签恢复为正常 Markdown 后交给现有 Dataview 解析；Dataview 查询正文的能力仍受其原生功能限制。全文检索直接使用 Obsidian 原生搜索。
- 解密前显示“准备中”；文件生成完毕后显示“等待索引”，通过目标文件解析/索引状态核验再宣布可查询。超时、部分文件失败时列出缺失范围，不能把不完整结果冒充全量。
- 默认全量解密 Markdown 和文档信息；图片/PDF等按需解密到本会话目录并改写临时链接，提供单独的“包含附件”选项。记录原始链接映射，回写时逆向转换，不能把临时目录路径保存到正式密文正文。
- Dataview 的任务勾选和原生编辑允许修改临时 Markdown；由会话管理器监听变化并纳入加密检查点，不能和原加密看板同时改同一篇文件。

### 11.4 开启、编辑和结束流程

1. 用户主动开启并输入一次口令；显示范围和数量。检查临时目录未被 Git 跟踪、忽略规则已生效，读取目标密文版本并建立不含正文的恢复日志。自动化代码不能把固定临时路径当成可随意覆盖的目录，发现已有文件先识别会话归属。
2. 后台分批完成认证解密；每篇完全验证后才创建其明文工作文件。失败不覆盖对应密文。显示进度和取消；取消时清理仅由本次会话新建且未被修改的副本，对已编辑内容先走保存流程。
3. 分批等待原生元数据及 Dataview 索引跟上，避免文件事件洪峰。会话内复用已授权的密码派生计算结果和必要内容密钥，结束时释放；不存到配置、Git 或日志。
4. 临时工作区修改采用合并监听与后台加密检查点，保持密文恢复基线尽量新；在状态中区分“临时文件已保存”与“密文检查点已保存”。暂不自动把工作区删除解释成正式删除，暂不自动导入任意新增文件；将新增、重命名、删除列为待处理差异，避免误删数据。
5. 点击结束、超时、锁屏或休眠触发结束流程：先停止新操作并关闭/遮挡相关编辑和查询视图，捕获未提交编辑，冻结本会话文件快照。原生编辑器和 Dataview 写回的实际收尾能力要在原型中验证；加密前后复核文件摘要，检测到仍在写入就重试或报告，不能读到一半即删除文件。
6. 对有修改的文件重新解析、加密，安全写入并重读校验，保留原密文至校验成功；未改文件保持原密文字节不变，避免仅查询一次就产生全目录 Git 改动。附件修改按同样流程处理。
7. 逐文件完成“正式密文验证成功→再次核对临时文件未变→删除本会话明文副本”，不用回收站保留第二份。本机或外部程序仍在修改、文件被占用、磁盘写满、校验失败时保留恢复资料并显示“清理未完成/仍有明文”，不能误报锁定完成，也不能为强行清理丢掉新修改。
8. 完成下面的索引、结果与已知缓存清理后，释放密钥与内存数据；回到全部分区锁定。全量结束耗时随文件数增长，先即时显示进度，不承诺锁屏/关机前一定完成所有 I/O。

### 11.5 Git、缓存与中断恢复

- 将 `周记/_临时解密/` 写入仓库同步的 `.gitignore`，开启前检查该路径及子文件不在索引内。若已有跟踪项，停止创建明文并报告；不自动改 Git 历史。建议交付安装用 Git 提交检查脚本，其他电脑需执行一次安装，因为钩子不会随普通 Git 克隆自动启用。`.gitignore` 仍不能阻止用户强制添加或其他程序复制。
- 临时模式期间不建议 pull；若 Git 或其他进程改动原密文，结束时校验原版本，保留双方数据并报告冲突，不能覆盖远端改动。提交功能只包含密文及公开运行文件，Git 钩子可阻止未结束会话的误提交，但用户仍可绕过钩子。
- Dataview 持久缓存必须针对临时路径清理。当前实现删除文件时主要移除内存索引，不能假定已经清除 IndexedDB。实现一个针对验证版本的窄适配层，移除会话路径的 pages/tags/links 等内存记录、持久条目，并防止未完成导入在清理后再次写入；不全库重建、不清空其他笔记缓存。适配层需验证任务收尾及重启后残留，在未知版本上不宣称缓存清理成功。
- 刷新/关闭受影响的原生搜索和普通 Dataview 结果视图，清理临时标题映射。任意 DataviewJS 可能把数据另存到全局变量、普通笔记或其他文件，无法保证主动收回这些副本；不能承诺“重新加密等于所有插件记忆清零”。
- 原生文件恢复、其他插件与系统索引可能另留副本；Apex 备份按用户要求暂不处理。此模式承诺核验受控工作副本及已知 Dataview 缓存的清理，不承诺 SSD 取证级擦除或所有插件副本清除。文件恢复的选择性排除能力需在原型核验，不能假定公开 API 已具备；若没有，报告具体残留边界，不静默清空全库历史。
- 崩溃、断电、强制关闭可能留下临时明文。下次启动仅轻量检测会话日志，优先显示“上次临时解密未结束”，由用户输入口令继续加密/核验/清理；不得自动删除尚未保存的修改，不自动重新解密整个目录。电脑处于关机/Obsidian 未运行时，插件无法执行清理。

### 11.6 本轮新增的验收

验证“主动开启→分批索引→原生搜索/DQL查询→Dataview 勾任务或原生修改→结束→独立脚本恢复”的完整链路；核验模板、frontmatter、正文、链接和附件一致。只查询不改内容时，正式密文的 Git diff 应为空。

另外覆盖临时路径未被 Git 跟踪、索引不完整、同名文件、写入冲突、锁屏、磁盘写满、文件占用、解密中取消、清理中崩溃和下次启动恢复；检查结束后磁盘工作目录、Dataview 内存与 IndexedDB 不残留测试标记。第三方另存及 Apex 历史备份明确排除，不能把这些排除项写成已经清理成功。

## 12. 性能设计与验收

“不造成卡顿”作为实施约束，但不能在没有运行测试时保证任何电脑、任意数据量及任意 DataviewJS 都零卡顿。将本功能新增开销与 Obsidian/Dataview 原有开销区分，按用户较慢电脑上的基线测量后验收；不通过则不迁移真实笔记。

### 12.1 启动与日常使用

- 启动仅注册视图、命令和事件；不解密、不运行密码派生、不建立全量索引、不加载附件。使用 Obsidian 已有文件清单列出随机 ID，避免递归扫描全库；文件头只在需要时读取。
- 加密 Worker 延迟加载，未使用时不启动；不增加第二套全量查询引擎或全库索引。锁定空闲时不周期扫描文件；超时仅用轻量计时/事件处理，不用短间隔轮询。现有 Dataview 的启动行为仍计入原有基线。
- 普通看板只解密当前展开分区，不渲染折叠分区正文；大型表格分批构建。原生 Dataview 结果渲染由其自身控制，对常用大结果查询提供筛选/限制行数的调整建议，不能宣称本插件能统一虚拟化任意 Dataview 视图。
- 编辑先更新当前内存模型，建议停止输入约 500 毫秒后合并保存，连续编辑最长约 2 秒提交一次，避免不断延后；收起/关闭立即提交。仅重加密变动分区；内容密钥保留到该分区锁定，不能每按一次键都重做密码派生。
- 一个周记一个写入队列；快速操作合并为最新快照，避免无限堆积。文件变化只刷新相关对象，不全量扫描和重渲染整个工作台。

### 12.2 全量操作与资源控制

- 本模块的密码派生、加解密和正文解析放入专用 Worker/后台任务。现有 Dataview 查询保持其原生执行方式，不能承诺搬移任意查询到后台。单纯把函数写成 `async` 不代表同步解析脱离主线程，禁止用无上限 `Promise.all` 开启整库任务。
- 默认 1 个工作任务，性能验证后最多放宽到 2 个；分批处理中间让出执行机会。后台线程同样消耗 CPU，需限速和取消，不能只以“主线程不卡”判断电脑没有负担。
- 同一域/口令版本批量解锁复用一次昂贵密码派生，随后仅执行快速解包；退出/取消后不留可复用全库根密钥。普通分区重新展开仍需重新输入并验证密码。
- 每批初始约 5–10 篇小笔记，按字节数、原生元数据和 Dataview 索引进度自适应；索引落后或界面出现长任务时减速并暂停新建文件，避免一次写出上千个 `.md`。进度、耗时和取消按钮可见；取消立即停止派发，随后清理/保全已生成文件，不能将“已取消派发”冒充“明文已全部清理”。
- 本模块从 64 MiB 在途解密/解析数据预算起步，仅保留当前批次、必要密钥和变更摘要，不保留完整明文目录的第二份内存副本；这是任务调度预算，不是 Electron 或 Dataview 的进程内存硬上限。单文件与附件另设大小限制，超限先提示再决定操作。
- 文件生成/删除与会话状态变更进行合并处理，不反复调用 Dataview 全库 `reinitialize`。不能利用文档化 API保证原 Dataview 只刷新一次；通过批次限速减少重复计算，必要时建议先关闭高开销查询视图，索引完成后再打开。若仍超预算，允许用户主动改用选定周记范围，界面显式标注范围而非静默漏数据。
- 对常用查询建议先筛选来源、减少显示行数，例如默认示例 `LIMIT 100`；但 LIMIT 不必然减少排序/聚合的计算量，仍需测量。可以取消本模块加解密队列，不能承诺中止已经在主线程运行的任意 DataviewJS 死循环。
- 默认只批量解密文本；大附件按需读取/导出，设置预览缓存总量和逐出策略。大文件需要设计经过测试的分块容器或明确首版大小上限，不直接把多个大型附件一次性载入内存。

### 12.3 可复现验收目标

以下为开发验收目标，不是已测结果；以记录硬件信息的较慢目标电脑、相同 Obsidian 与插件组合对比基线，分别测试冷/热启动、查询、编辑和空闲。

| 项目 | 测量/初始目标 |
| --- | --- |
| 启动额外开销 | 锁定默认启动无密码派生/全文扫描；同条件多次对比，中位启动增量目标不超过 100 ms，并记录 P95 |
| 主线程响应 | 本模块常规批处理切片约 5–10 ms；常规交互不新增持续 50 ms 以上长任务；记录输入和滚动响应 |
| 分区解锁 | 口令派生有意消耗时间；目标较慢电脑约 300–800 ms 级，实际由安全下限/硬件决定，等待期间 UI 可操作，不承诺恒定耗时 |
| 取消与结束 | 点击后约 100 ms 内出现反馈；约 1 秒内停止新增派发；已生成明文需继续加密核验/清理并显示进度，不能承诺全库一秒锁定 |
| CPU | 锁定静置不持续消耗加密/扫描 CPU；批量任务不无上限并发，不以吃满所有核心换速度 |
| 内存 | 用 520 篇、合计约 20 MiB 文本的数据，对比“相同普通 Markdown 已被原生/Dataview 索引”的基线，隔离本模块额外 RSS，初始目标不超过 100 MiB；同时记录相对锁定状态的总内存增量，不掩盖原生索引成本 |
| 长期使用 | 反复解锁/锁定 30 次，受控对象/Worker/监听器数量回到基线附近，无持续增长；RSS 不要求立即回落，因为 GC 时机不可控 |
| 扩容与附件 | 52/520/2000 篇分档，加入少量超大笔记和大附件，验证不会启动时全加载，超限时清楚降级 |
| Dataview | 常用原生搜索、DQL 和任务编辑对比普通 Markdown 基线，测分批导入/清理期间响应；不能为任意复杂 DataviewJS 承诺可取消或零卡顿 |

全量解锁总耗时随文本量、分区数量、硬件和查询复杂度增长；提供进度比承诺固定秒数更可靠。性能达标以实际记录为准，预算不达标时优先改任务调度、批次和数据结构，不降低加密强度。

Dataview 官方也说明复杂查询可能冻结 Obsidian，尤其在大库下：[查询结构与性能说明](https://blacksmithgu.github.io/obsidian-dataview/queries/structure/)。
