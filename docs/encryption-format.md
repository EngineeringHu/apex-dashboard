# Apex protected formats v1 and v2

The executable reference implementation is `apex-crypto.mjs`. This format and the plugin are not independently audited. Both versions are supported by the current desktop plugin and standalone exporter. Current filenames are readable, user-selected names; legacy files used UUIDs. No Obsidian configuration is required for recovery. The following describes v1; v2 differences are specified below.

An `.apexenc` file is UTF-8 JSON plus an optional trailing newline. Fields are `format: "apex-protected"`, `version: 1`, `id`, `domain: {salt, iterations}`, `blocks`, and `manifest`. Salt is 32 random bytes, base64 encoded; PBKDF2 iterations are 600000 (read limit 2000000), hash SHA-256, output 256 bits. Password encoding is UTF-8, no normalization. The resulting bits are imported as an HKDF key and discarded as raw bytes.

HKDF-SHA-256 uses UTF-8 file UUID as salt and UTF-8 `apex-protected/v1/<purpose>` as info. Purpose `manifest` produces the manifest AES-256-GCM key; purpose `wrap/<block-uuid>` produces an independent wrapping key. GCM uses 12 random nonce bytes and a 128-bit tag; the encoded ciphertext includes the tag as produced by Web Crypto.

Each block has `id`, `kind` (`info`, `table`, `text`), `key` and `data`. `key` wraps a random 32-byte content key. `data` is the encryption of UTF-8 JSON `{raw, title?, definition?, assets}`. The first and only `info` block stores text before the first H2 heading and the real filename title. Subsequent blocks store their exact heading and Markdown text. Code fences and frontmatter do not split sections. Concatenating each decrypted `raw` reconstructs the document without normalizing whitespace or line endings.

All authenticated additional data is UTF-8 `JSON.stringify(["apex-protected",1,fileId,domain.salt,domain.iterations,label])`. Labels are `manifest`, `key/<blockId>/<kind>`, and `data/<blockId>/<kind>`. The authenticated manifest plaintext is `JSON.stringify(blocks.map(b => [b.id,b.kind]))`; it authenticates membership, kind and order. It does not prevent replay of an earlier valid file or earlier valid ciphertext for the same block. Version conflicts are handled separately in the storage layer.

Assets are separate JSON files at `_assets/<assetId>.apexasset`: `{format:"apex-asset",version:1,id,data}`. They use a random AES-256-GCM content key; AAD is UTF-8 `apex-asset/v1/<assetId>`. References `{id,key,link,name,mime}` appear only within encrypted block payloads. `key` is the base64 raw asset key; `link` is the original Markdown link token. Repeated block references may share an asset; first-version ciphertexts are immutable unless a new asset is explicitly imported. Original asset names and MIME are encrypted in the references.

Decoder limits: note text 4 MiB, envelope 12 MiB, attachment 32 MiB, at most 512 blocks. Unknown versions, duplicate IDs, malformed domains and failed authentication must reject before writing plaintext output. The independent exporter authenticates all blocks and all referenced assets before creating its output.

The worker retains content keys (including the metadata block key) for unlocked individual sections. Batch/whole-document operations explicitly retain a root-key handle for their authorized lifetime; handles are random UUIDs and are revoked on lock. Plaintext private keys never reside in JSON settings. Worker termination drops all handles. JavaScript and OS memory erasure are not guaranteed.

## v2: password-protected recipient and public-key creation

The envelope has `version:2` and an additional `access:{recipient,wrappedRoot}`. `recipient` is also synchronized as `.apex-weekly-keyring.json` for future note creation. Each note embeds its own copy so independent recovery needs only the file and password (plus referenced encrypted assets). v1 files remain readable, but older v1-only readers must reject v2.

Recipient fields: `{format:"apex-weekly-recipient",version:1,id,domain,publicKey,privateKey}`. `id` is a UUID v4; `domain` uses the same PBKDF2 parameters described above. `publicKey` is base64 SPKI for a 3072-bit RSA-OAEP/SHA-256 key with exponent 65537. `privateKey` is the AES-256-GCM encryption of PKCS8 DER bytes using `purpose(passwordRoot,recipient.id,"recipient-private")`. Its AAD is UTF-8 JSON `["apex-weekly-recipient",1,id,domain.salt,domain.iterations,publicKey]`. Unlocking authenticates the private key and tests that it matches the published public key. New passwords require at least 3 Unicode code points, at most 1024 UTF-16 code units; no normalization.

Creating a note requires only the public key. Generate a fresh random 32-byte root, wrap it using RSA-OAEP/SHA-256 with label UTF-8 `apex-note-root/v2/<fileId>`, and encode the resulting 384 bytes as `wrappedRoot`. Import the root into HKDF, discard the raw bytes, and create/sign blocks as above. Validate the complete round-trip before publishing. No password or reusable decryption root is kept for future creation.

For decryption, derive the password root, decrypt/import the recipient private key, and unwrap the note's root. Envelope `domain` must match the recipient domain. Block AAD uses the actual envelope version (`2`) instead of `1`; the HKDF info prefix intentionally remains `apex-protected/v1/` for the shared block implementation. A wrapped root is bound to the note ID, preventing its substitution between notes. Assets retain format version 1.

Changing the unified password creates a new recipient and reencrypts each note in a Worker, preserving note IDs, section IDs, exact payloads and asset references. Each staged result is decrypted with the new password and compared before replacing originals. `.apex-weekly-rotation.json` records per-file before/after hashes and staged ciphertext paths, enabling interrupted replacement to roll forward. Conflicting externally modified files halt recovery instead of being overwritten. Staging and the journal contain no passwords or plaintext bodies and are excluded from Git. Historical Git revisions retain their original passwords.

Batch temporary decryption may keep a recipient private-key handle for the authorized session to avoid repeating PBKDF2 per note; each note still unwraps its own root. Ordinary section unlock discards the root/private key and keeps only that section and metadata keys. Closing/collapsing revokes these handles; new section expansion asks for the password again.
